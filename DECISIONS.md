# Decisions

## Summary

- The dashboard is for Nimbus's technical team, who manage pricing for their own product.
- Pricing derivation stays in pure, tested functions in `lib/derive`, separate from the interface.
- Only features are versioned; price, credits and exhaustion policy affect all customers at renewal.
- The Overview gives a concise picture; plan detail explains pricing, features and version history.
- Comparison answers what separates the selected plans or versions.
- Plan creation and in-place editing show customer impact before publication.
- Confirmed migration updates customers immediately in this prototype; a real system would apply it at renewal.
- Catalogs live in `localStorage`; `data/catalog.ts` seeds Nimbus and Reset demo restores that seed.
- Colour carries meaning in the dashboard; onboarding holds the more expressive animation.
- Pack management, catalog feature creation after onboarding, a real backend and cross-tab synchronization are outside scope.

I use this document to explain my current implementation choices, their trade-offs and the limits of the prototype. I keep final decisions here rather than a history of discarded designs.

## Plan comparison

- **Detail URL continuity.** I read edit, compare and diff from useSearchParams on both server and client, without environment-dependent route fallbacks. Draft controls and source selection live in PlanEditorSession; PlanDetailEditor owns the live catalog, publication and confirmation. Full publications remount the session; standalone customer moves keep unsaved controls and the editing URL intact.

- **Header action sizing.** I give Compare, Create plan and Edit plan the same 44px minimum height and vertical padding, preserving icon-aware horizontal spacing and the filled primary Edit treatment. The shared header keeps this sizing in ordinary detail and comparison.

- **Editing and comparison integration.** I resolve both modes through the same detail controller against the active stored catalog for Nimbus and local companies. An explicit edit request opens the current feature version and takes priority over comparison. Entering editing clears comparison/filter parameters; comparison links clear edit/migration state. I use the live browser URL after mode changes so Discard cannot restore a stale comparison. I order header actions as Compare, Create plan from the selected plan, then the primary Edit plan action, keeping the comparison entry out of Features. Scheduled migration records and the store publication callback remain connected to editing.

- **Plans or versions, one reference.** I compare another plan or another version of the open plan against its selected version. The left side stays the reference; the right side always describes the compared configuration. Every card and feature table names both plans and versions. The selector lists the open plan's other versions first, omitting the left-hand version, then other plans in pricing order. Its default is the current version when available or the newest alternative. Same-plan comparisons share plan-wide prices and customer totals while feature impacts distinguish the versions. Private plans remain available and are labelled private.
- **Shareable reading mode.** I use links with compare=code.version, version=N and diff=1. Missing comparison versions fall back to that plan's current version; unknown targets leave the ordinary detail visible with an unavailable message. An identical comparison remains valid and shows equal values, including the no-differences state. The URL owns comparison selection. Initial Nimbus HTML uses the seed; the shared client controller resolves the query against the live updated catalog after hydration and publication, so saved feature versions and customer moves remain comparable. Comparison components and calculations also ship to the client.
- **Persistent comparison controls.** I open the comparison selector as a panel sliding from the right, matching the review panel's 44rem width, full-height card surface, header spacing, textual Close action and black 50% scrim. The explanation belongs to the body so it does not enlarge the header. It fills the width on phones, retains Escape/light dismissal and marks the chosen version. During comparison, a continuous right-edge button spans the space between the top bar and bottom action bar, with three centred left-pointing chevrons and an accessible opening label. I reserve its width in the content. I place Exit compare in a fixed bottom bar alongside the compared plans and feature-difference count, following the edit bar's placement. A small client component measures only the bar height to reserve content space, scroll padding and the rail's lower boundary, including wrapped labels, zoom and mobile safe areas; comparison selection remains URL-owned. Panel movement becomes a short fade for reduced motion.
- **Customer meaning, shared rules.** I derive paired feature rows in lib/derive and use compareFeatureValues for impact relative to the left side. Equal values have no impact label. Absent and disabled access both mean not included, so they are equal. Opposing capacity and overage changes retain the existing trade-off classification, with an icon and text.
- **Plan-wide prices and totals.** I preserve independent monthly/yearly prices, credit allowances, unit prices, exhaustion policies, packs and customer distributions. I colour individual differences with the existing customer-impact tokens: lower price/unit cost and more credits are better, the reverse is worse. A lower overage price is better; switching between blocking and billing overage is a trade-off, because one never bills extra but stops the service and the other keeps it running at a cost. Comparison and editing share this rule through one derive helper. Arrows, directional wording and accessible impact labels accompany colour. Customer counts, billing availability and different pack configurations use informational blue without claiming a customer benefit. I assign no overall winner to a higher price and allowance. Pricing and customer totals are plan-wide even when an older feature version is selected.
- **Continuous card bodies.** I make each comparison card a flex column whose split body fills the remaining grid-row height, keeping both value halves and their separator continuous down to the bottom. I retain equal body padding and omit empty alert containers instead of reserving space for absent notes.
- **Mobile reference labels.** I use slightly larger semibold ink text for each plan/version label in stacked cards and feature rows, making the reference clear before its values. Desktop retains the compact muted labels.
- **Mobile feature boundaries.** I place a stronger 2px rule below each feature title and separate it from the first plan value. This distinguishes the start of a new feature comparison from the lighter line between its two plans. Desktop retains the table's ordinary row separators.
- **Selection continuity.** I finish the selector's 180ms exit before its link navigates, preventing replacement from cutting off the panel animation. Modified clicks retain native navigation. On entry, card surfaces and the bottom bar fade for 150ms; right-hand values fade and move 6px over 220ms together, without staggering or animated numbers. Subsequent target changes animate only the right-hand values; filtering does not replay motion. Small client boundaries own timers and Web Animations; comparison values derive from the active catalog and the URL owns selection. Unmounts and rapid target changes cancel pending work. Reduced motion uses 150ms fades without translation.
- **Configuration over history.** I hide the Versions timeline and historical diffs during comparison because the question is what separates two selected configurations. Left-version navigation preserves comparison and filtering. Customers retain totals and distributions without the retired-version warning, which belongs to plan history. I use a plain comparison heading rather than an explanatory banner. Exhaustion warnings stay beside the policy; data problems remain visible beside Features.
- **Responsive pairs.** I use two summary cards per row on wide screens and three full-width feature tables in sequence. Below the small breakpoint, both card halves and each feature row's values stack left first with repeated plan/version labels. Tables retain explicit semantic roles when their display changes; impact uses text/icons as well as tokens.
- **Difference filtering.** I filter only feature rows through diff=1, retain all pricing/customer context and show an explicit no-differences state for empty groups. Exit compare removes both comparison parameters while preserving the selected left version.
- **Independent modes and composition.** I give explicit edit requests priority over a comparison query and rebuild comparison links without edit state. I expose optional action slots around the existing create-plan link, placing comparison before creation and the primary action afterward. The separate comparison view reuses existing formatting, impact labels, alerts and visual tokens while leaving ordinary pricing/features/history components intact.
- **Verification boundary.** I test pure selection, impact direction, unavailable features, capacity trade-offs, unlimited values, independent billing periods and URL transitions. Static markup tests cover labels, action order, native popovers, filtered empty states, organization-scoped links and hidden history. These checks do not verify browser layout, focus or mobile interactions.

## Data model and derivation

- **Pure display logic.** I keep the supplied Catalog and source data unchanged. I derive summaries, comparisons, alerts and draft checks in lib/derive without React or side effects, so overview, detail and creation reuse the same rules.
- **Explicit availability.** I resolve every catalog feature in catalog order. I treat an absent release feature as not included, with the same clarity as a boolean set to false.
- **Pricing scope.** I keep prices, included credits and exhaustion policy on the plan, and explain that changes affect all its customers at renewal. I keep features on releases and preserve the version each customer subscribed to.
- **Independent periods.** I read monthly and yearly prices and credits separately, never deriving one from the other. I treat Free's allowance as monthly because its pricing has no interval, and show no yearly period for it.
- **Amounts and formatting.** I store money in cents, keep fractional cents in comparisons until display and format through lib/format. I omit .00 for whole amounts and use English, en-US and UTC to keep server/client output consistent.
- **Customer impact.** I classify availability changes as added/removed and changes to an available feature as changed. I reuse compareFeatureValues for version diffs and checks: lower credit cost, more capacity and gaining access are better. I label opposing capacity/overage changes as a trade-off instead of inventing an objective winner.
- **Defensive totals.** I count subscription rows only when they join to an existing release and surface orphan rows as data problems. I use the largest remainder method so nonempty whole-percentage distributions total 100%.
- **Neighbours and warnings.** I include private plans in comparisons, label them private and place equal-price neighbours below the draft. I define most customers on retired versions as strictly more than half across all retired releases. I omit credit-price savings against Free. A free draft has no credit price to compare with any neighbour. Because equal-price plans sit below the draft, checks and labels say a same-price neighbour costs the same rather than less.
- **No invented metrics.** I omit revenue, MRR and trends because billing intervals per customer and historical data are missing. I show capacity overage per unit without inventing a period, and infer replacement from the next published release because retirement dates are absent.

### Data observations

- I noticed that Growth has 352 of 398 customers on retired versions and only 46 on v3. I show the real split rather than assuming the current release represents most customers.
- I noticed that Growth v3 matches Scale v1 on boolean features and image-generation credit cost. I present the remaining differences without implying every feature improves at every price step.
- I noticed that Enterprise is private and described as negotiated, but the catalog still supplies fixed prices. I show those values without inventing contracts.
- I noticed that larger packs are only slightly cheaper than overage and also expire. I show the saving and expiry without calling packs universally better.
- I noticed that Free blocks at exhaustion and offers no pack. I explain upgrading as its only configured way to continue rather than modifying the source data.
- I noticed a common 10× yearly-price / 12× credits pattern. I use it as an optional reference, never an automatic derivation.
- I distinguish the default plan from a price's default interval despite both using isDefault. I validate release/subscription consistency rather than assuming the sample is always valid.

## Dashboard shell and visual system

- **Internal dashboard.** I design for the Nimbus team managing pricing, not its end customers. I use a sidebar, top bar and content sheet; Plans links directly to each plan and New plan rather than a duplicate index.
- **Identity and controls.** I use a Nimbus admin placeholder because authentication is outside the exercise. I paint the Commet mark through an ink-token mask and omit controls without implemented functions, including search, settings and sidebar collapse.
- **Native interactions.** I use dialog for mobile navigation, the Popover API for alerts and details for the Plans group. I label them and handle focus, Escape, dismissal and link navigation while the shell remains mounted.
- **Alerts in context.** I count warning/data-problem alerts in the bell and place flags/explanations next to the affected plans and data. I do not repeat them in a separate overview alerts section.
- **Tokens and typography.** I replace Tailwind's default colour/radius palettes with semantic tokens. I use IBM Plex Sans through next/font, tabular figures and decorative SVG icons without an icon library.
- **Shared desktop scale.** At viewport widths of 1280px and above, I set the root font size to 112.5%. Rem-based type, cards, controls, shell dimensions, spacing and the 88rem content cap scale together; at the usual 16px browser default, the base is 18px and the content cap is 1584px. I scale the onboarding headline's fluid desktop value by the same ratio so its viewport-based size follows. I retain the normal base and touch sizing below this width and keep browser zoom/font preferences available. I use no CSS zoom or whole-interface transform, preserving physical viewport heights and measured menu/transition coordinates. This approximates a more compact desktop view; browser-zoom breakpoints can still differ.
- **Dark first, optional light.** I override the same tokens for light, apply the stored choice before first paint and keep server-rendered controls independent of storage. I suppress unrelated colour transitions during theme changes.
- **Dark green continuity.** I use the onboarding's dark dollar green (#50765a) for current-version bars, legend dots, focus and selected-step fills through live/live-soft in both dashboard themes. I separate live-ink for readable status text (#8fb29b in dark, #50765a in light) and on-live for white text on dark green fills, keeping the onboarding's light selected-step fill paired with dark text. I retain neutral customer-distribution segments, striped grey retired versions and separate warning/impact labels. From the declared opaque tokens, I measure current-state text at 7.96:1 on dark cards and 4.68:1 on the light sheet; white on the dark green fill is 5.15:1. I do not claim rendered/translucent browser coverage from those calculations.
- **Depth and accessibility.** I separate sheet, card body and header surfaces. I pair status colours with text/icons, stripe retired versions and supply text legends for decorative bars. I retain semantic headings, labels, visible focus and touch targets.
- **Restrained polish.** I use concentric radii, optical icon padding and press feedback that excludes disabled controls/reduced motion. I animate the small sidebar disclosure's height because the following link must move with it; unsupported browsers open it instantly.
- **Route titles.** I derive top-bar breadcrumbs from routes/catalog names, keep semantic page headings visually hidden and mark animated titles decorative. I show the first title whole for hydration and omit subtitles that merely repeat it.
- **Attention without repetition.** I ring the bell once per browser session when warnings exist, not on every navigation. I keep theme-icon and organization-switcher feedback short and reduce positional movement when the system requests reduced motion.

## Overview

- **Empty customer populations.** I treat zero customers as normal for a new company, plan or release, including a retired release emptied by migration. I show the zero total and empty version bar without a no-customers alert or warning style; data inconsistencies and customers concentrated on retired releases still raise alerts.
- **Credit pack availability alignment.** I let each pack's availability list fill its shared grid section and anchor the unavailable-plan note at the bottom. Notes align across cards with different numbers of available plans, without fixed heights; stacked cards keep their natural content height.

- **Customer context first.** I put distribution inside the wider Customers stat instead of a separate section. I derive the context from the largest segment, followed by Paid customers and On retired versions; those two cards share a row below Customers on phones.
- **Paid is a domain classification.** I count pricing types other than free, including private Enterprise. I do not infer this from the monthly price or claim the count represents collected revenue.
- **Neutral distribution palette.** I use theme-specific grey ramps instead of giving unrelated meanings to plan colours. I hide the decorative bar from assistive technology and list every plan's count/share in a text legend, so interpretation does not depend on colour contrast alone.
- **Small segments remain visible.** I keep a 2px segment minimum and show <1% for nonzero counts that round to zero. I spread paid plans across available ramp steps; additional plans can share a step because the legend identifies them.
- **Comparable plan cards.** I use an ordered list with five aligned CSS subgrid rows: name/visibility, monthly price/comparison, credit allowance/unit price, a compact exhaustion policy, and customer count/version bar. I stack cards on phones and scroll the card row inside its container when necessary. I keep one stretched name link and one focus stop per card. I remove descriptions, price/credit deltas, pack lines and long status legends from this summary; details retain the deeper information. I show compact version percentages directly below each plan's bar (v1 15% · v2 85%), highlight the current version's text and let version/percentage pairs wrap together. I show <1% for a nonzero count rounded to zero, keep the complete accessible status/count summary without announcing the visual labels twice, and preserve the empty-customer state.
- **Monthly overview, yearly detail.** I focus the ladder on monthly pricing and show independent yearly values on detail pages. I show only per-credit savings against the cheaper paid plan, omitting the comparison when credit prices cannot be compared. I shorten overage to / 1k with an expanded unit label and keep the policy term available to screen readers.
- **Warnings and packs.** I mark affected cards with a warning-colour border and header tint, then explain the reason with a warning icon and text below the customer bar. Colour is not the only signal. I keep pack comparisons on detail pages and the dedicated packs route, including savings versus overage, expiry and plan availability, instead of repeating them on overview cards.
- **Tests.** I cover distribution, empty/invalid subscription joins, paid totals, ramp mapping and per-credit savings with pure tests alongside the existing derive coverage. I render compact cards to static markup to check values/comparison/policy, accessible version summaries, zero customers and missing monthly prices; this does not verify browser geometry.

## Plan detail

- **Pricing without a repeated heading.** I open the detail with its summary cards below the create-plan action, using a 1rem gap rather than a visible Pricing heading and long introductory note. I retain the semantic heading and renewal-scope note for screen readers, without taking visual space. I place alerts beside their relevant pricing/version information and keep features above history.
- **Configuration before history.** I put Features immediately after Pricing and move the Versions timeline/diffs below it. I add the shared per-version customer bar and compact percentage labels inside the Customers pricing card, using the plan's full distribution independently of which feature version is selected. I keep the existing current-version count and empty state for context.
- **Versions with changes.** I show the timeline and consecutive diffs newest first, with dates, customer counts, availability and labelled impact. I provide an explicit empty comparison state for a single version.
- **Feature tables.** I group credit, capacity and access into semantic tables, show not included as clearly as included and avoid invented overage for unlimited capacity. I show today's value beside differences on an older version.
- **Shareable selection.** I place a labelled View version control directly below Features, using wrapping links with 44px minimum height and a distinct green selected state. Current identifies the live release independently of selection; a single release needs no switcher. Version queries resolve against the stored catalog. Invalid versions fall back to the current release, and missing plan codes show the shared client missing-plan view. I avoid a server 404 based only on the seed because saved plans exist only in this browser. I retain separate impact and status tokens.
- **Shared wording and tests.** I reuse pack/exhaustion descriptions and test single versions, absent features, capacity policies and invalid version selection. I render detail markup to verify Pricing → Features → Versions order, customer chart percentages, labelled version query links, selection styling and single-version control omission. Browser layout/zoom checks remain separate from these tests.

## Create plan

- **Saved plan completion.** I show a Plan created screen only after the store accepts the write. It names the plan and v1, explains browser saving or session-only fallback, highlights the ladder entry and offers actions to view the plan, return to the overview or start another empty draft. Failed writes retain the form and its error. Starting another clears the draft's base and step URL parameters; onboarding retains its collection flow.
- **One draft.** I keep state in CreatePlanFlow with a reducer over DraftPlan; steps, checks and ladder share it. The shared stored dashboard resolves base selection against its current catalog. Nimbus starts with the seed and rebases draft content once after hydration, preventing stored prices or features from leaving a seed-based draft behind. Local companies open the same flow after their catalog loads.
- **Missing is not zero.** I track pending fields separately from domain placeholders, preserve unfinished input and avoid treating an empty price as intentional zero. I validate forward navigation, allow backward navigation and focus the first invalid field after its error renders.
- **Step navigation.** I use history.pushState and a step query parameter so browser Back moves through the flow without a server round trip. I clamp requests to the first incomplete step and start drafts fresh after reload; I persist completed companies and plans, not unfinished drafts.
- **Identity and bases.** I generate the code from the name until manually edited, validating format/uniqueness. Clearing the code returns subsequent name edits to automatic generation. I copy a base's pricing, policy and current features, not its identity, and ask before overwriting edits. I omit base selection for empty catalogs.
- **Yearly and comparisons.** I make yearly billing opt-in with separate price/credits. I offer a ratio suggestion only when existing plans agree, compare with real neighbours and wait for completed numeric inputs before sanity checks.
- **Exhaustion and packs.** I explain the customer experience before each policy choice and start scratch drafts without a choice. I choose packs in that step because they change the meaning of running out. I suggest shared neighbour packs, or the other's when one has none, until manually overridden; restoring the suggestion is explicit.
- **Configuration, not pack management.** I do not create or edit packs. Saving a plan in Nimbus or a local company associates selected existing packs with it in the same stored catalog. I list all features by type with explicit inclusion, credit cost and capacity policy, reuse neighbour/impact rules and validate incomplete feature numbers.
- **Live ladder.** I show it beside the form on wide screens and as a collapsible summary on phones. I debounce placement by 350ms, leave an unpriced paid draft unplaced and animate reordering with cancelable FLIP transforms. I announce placement once.
- **Review and browser publication.** I group checks by severity, link to their steps and summarize decisions with Edit actions. I block only for blocking checks and explain customer impact. Every dashboard publication uses the store: creation saves the plan and shows its completion screen; editing saves catalog, effective moves and readable scheduled operations saved in the browser with an earlier format together. I explain browser persistence and the session-only fallback.
- **Purposeful motion.** I reuse the emphasized easing for short step transitions, measured-height reveals and ladder changes. I keep manual numeric edits/readable comparisons still, clean up interrupted animations and use gentler reduced-motion variants.
- **Tests and dependencies.** I use Vitest for pure derivation, reducer, validation, route titles and amount parsing. I upgraded @types/node to meet its peer requirement and add no runtime animation/UI dependency.

## Inline plan editing

- **Visible publication success.** I close editing and migration with a positive check mark paired with Changes saved, a result-specific panel title and prominent effective customer counts. I separate immediate customer moves from plan-wide renewal effects, keep persistence details as a quiet footer and provide Done within the panel. I use Changes applied for memory-only or preview results rather than claiming browser saving. The existing dialog exit and focus restoration remain shared with Review.
- **Panel and discard transitions.** I animate occasional pointer-triggered Review, migration and confirmation panels with opacity and an 8% horizontal entrance over 250ms, paired with a 200ms backdrop fade and matching 200ms exit. I reuse the existing emphasized easing and native dialog rather than adding a motion dependency. I keep the background inert until exit completes, cancel pending close timers on unmount and restore focus afterward. Discard immediately restores the reading state and reveals it with a 180ms fade and 4px offset, without animating layout or delaying the reset. Keyboard-triggered actions stay instant; reduced motion uses only a 150ms fade.

- **Migration destination control.** I use a custom destination combobox inside the migration panel so its menu follows the dashboard surfaces, borders and green selected state in both themes. I mark the selected version with a check as well as color, keep the selected value in its accessible name, support arrows/Home/End/Enter/Space and close with Escape, Tab or outside interaction. Escape closes the menu before the panel; keyboard navigation keeps the active option visible. I add no dependency.

- **Customer context while editing.** I keep the version bar and a compact table with version status, exact customer counts and percentages, hiding the duplicate percentage line beneath the bar in editing. I show only No changes yet for an untouched draft; effective changes reveal just their relevant reach: all customers at renewal for price, credits or policy, and new customers receiving the prospective feature release. I emphasize these concise lines with the existing green treatment and provide accessible scope labels. Reverted or unfinished values do not imply a new scope. I consolidate grandfathering and optional migration into one bottom note, keeping the card compact without adding content to neighbouring cards.

- **Edit in context.** I edit the current release within the plan detail, replacing values with labelled controls in their existing cards and table cells. Editing from a retired release opens the current one first. I retain the read-only history and hide version navigation during editing so a draft cannot be mistaken for an older release.
- **Shared controls, one draft.** I share numeric, feature and policy controls with creation and keep one in-memory draft for identity, pricing, policy and features. I preserve price IDs/defaults and existing pack associations. Discard restores the original snapshot, including unfinished input text; reload discards edits.
- **Changes and scope.** I compare resolved features through the existing diff/impact rules, count each changed feature once and count general fields separately. I show before/after text and customer impact in changed cells, including independent capacity/overage impacts and the combined trade-off. I distinguish identity changes from renewal changes. Only changed features create a new release; pricing, included credits and exhaustion policy affect the actual total across all versions at renewal. I omit incomplete numeric fields from effective change counts rather than treating an empty value as an intentional zero.
- **Persistent editing context.** I show change count, prospective version and customer scope in a fixed bottom bar, reserve its measured height below the page and account for mobile safe areas and keyboard focus scrolling. I exclude the edited plan from neighbour comparisons and sanity checks.
- **Aligned pricing cards.** I stretch the editing summary cards to the tallest card in each grid row and let their bodies fill the available height. I keep controls aligned at the top, without fixed heights, so policy explanations, change marks and validation messages can grow naturally; mobile cards remain stacked.
- **Customer distribution and pricing context.** I use the same customer version bar in viewing and editing, with the actual total, current-version green, striped retired segments and an accessible count/status summary. I leave current counts unchanged while a migration is pending. I anchor the actual included-credit cost and each neighbouring plan's actual price/credits beneath monthly/yearly controls. I place the yearly price difference against twelve monthly payments directly below the yearly price input as a small muted hint, keeping its comparison basis accessible and reserving the same hint space under the monthly input on four-column layouts. This keeps both credit fields and the lower comparison sections aligned. Neighbours follow the draft's monthly position, exclude the edited plan and adapt to every catalog rather than naming fixed plans. I withhold incomplete-input calculations and mark an absent neighbour billing period as not offered. I compact policy choices to short radio labels plus an explanation of the selected option, retaining the surcharge field and unchanged pack associations.
- **Edit-mode continuity.** I soften pointer entry into editing with opacity and a 4px offset over 180ms, staggering identity, pricing and features by 30ms. I reveal the fixed bar with the same short transition. I use the existing emphasized curve and CSS starting styles, with no replay during value edits, no layout animation or dependency. Keyboard entry is instant; reduced motion uses a short fade without movement.
- **Deliberate scope.** I edit existing catalog feature configurations only. Adding new features to the catalog, changing the Free/paid billing type, adding/removing billing periods, changing price identities/defaults and editing credit packs or their associations remain outside plan editing. These changes need their own workflows and subscription rules.
- **Review scopes.** I compare against the current published release, show feature diffs with ImpactLabel, and separate new-customer features from plan-wide renewal changes with the actual subscriber count. Name and visibility get their own identity block. I reject no-op or invalid publication and preserve billing identities, periods, defaults and pack associations.
- **Immediate, confirmed migration.** I place Configure migration beside Review & publish in the fixed editing bar and keep destination settings, source selection and impact diffs in the side panel. For an existing destination, Done opens an explicit confirmation of the customer count, origins and destination; confirmation moves whole source populations immediately and saves the new distribution. It applies only the migration and preserves other unsaved plan controls. With feature changes, Done retains the selection in the draft and Review publishes the new release and its selected customer moves atomically. I allow forward moves only, default existing destinations to the current release and offer intermediate releases. Normal editing starts unchecked; selected sources count as changes. I highlight worse feature changes before confirmation and reject changed customer totals instead of moving a different population than confirmed. I make immediate migration a demo operation, while plan price, credit and policy effects retain their renewal wording.
- **Direct migration entry.** I link the retired-version alert to current editing with the migration panel opened and focused, without adding a header action. Populated retired sources open that panel with their version preselected. I keep the destination current on entry, scope URLs through the existing company link helper and remove entry query state when discarding or publishing.
- **Visible completed moves and earlier saved operations.** I update version bars, exact counts, percentages, history and retired-version alerts from the saved subscription distribution after confirmation. Immediate moves do not create scheduled operations. I continue reading scheduled operations saved in the browser with an earlier format so existing saved data is not lost; I do not apply them silently during hydration. Confirming a move from one of their origins replaces that operation, while unrelated operations remain intact.
- **Atomic local publication.** I save plan configuration, effective subscription counts and any retained earlier-format scheduled operations together in the existing organization-store envelope. A new release exists before assigning customers to it, and the total customer population remains unchanged. I accept older envelopes without schedules, validate saved operation references and counts, skip malformed or duplicate operations and reject stale plan drafts or changed confirmed populations. Storage failures retain the complete transaction in memory and are explained in confirmation.
- **Nimbus browser publication.** I publish Nimbus through the same store callback as local companies. Creation, plan-wide edits, new feature versions and effective customer moves survive reload when browser storage works. Confirmation explains browser saving or the memory fallback. Immediate moves update subscriptions without waiting for a renewal; I do not model a billing renewal process.
- **Implementation boundary.** I resolve live dashboard data in a client boundary because the catalogs live in browser storage. Nimbus still has complete server HTML from the frozen initial seed; hydration can replace that content with saved values, which is an accepted visible update. Local companies retain their loading view. I share reading, history and comparison components, native desktop side panels/mobile dialogs, focus restoration, Escape handling and scroll locking.

## Organization onboarding and form polish

- **Isolated company setup.** I open /onboarding from Add organization outside the shell. I build an empty catalog with the existing Catalog type, USD and no Nimbus features, plans, packs or subscriptions copied into it.
- **Welcome and handoff.** I use three phrases and reverse ordered-Bayer glyph dissolution, with stationary dark-green dollar traces over randomly chosen letters. I keep the accessible heading whole, hide decorative animation from assistive technology and provide Skip/reduced-motion behaviour before the labelled company-name field.
- **Reading time.** I set each automatic phrase's pre-exit reading time to 1470ms, including its existing entrance, and preserve the 850ms dollar/dither exit. The final heading remains until the company name is confirmed.
- **Shared onboarding scale.** I let the onboarding inherit the same larger desktop root scale as the dashboard rather than applying an additional local magnification. I keep the welcome at one viewport tall and its fluid headline viewport-based, with rem limits and wrapping following the shared scale. I preserve the existing 1470ms reading time and letter/dollar animation.
- **Continuity.** I retain the frame, measure outgoing intro content and wait for its 850ms dissolve plus a 100ms pause before the builder enters. I mark inactive content inert and fade the central halo out rather than retaining a light behind the forms.
- **Refractive glass.** I implement canvas-generated displacement/reflection maps inspired by [archisvaze/liquid-glass](https://github.com/archisvaze/liquid-glass). I keep text above the optical layer, regenerate maps on resize and use Chromium SVG refraction with a CSS/reflection fallback elsewhere. I use solid surfaces for reduced transparency/increased contrast, without a library or background image.
- **Natural feature questions.** I ask what customers do, what to limit or what access to offer. I suggest familiar English measurements such as generation, call, user and GB; unknown names get a visible use/item fallback, not an invented quantity. I configure costs/allowances later in the plan.
- **Editable suggestions.** I show grey measurement placeholder text and Use suggestion. I stop automatic changes after acceptance/manual typing and restore them when the measurement or feature name is cleared. I crossfade automatic suggestions over 180ms with a small offset, keep manual typing instant and remove the offset for reduced motion.

## Organization persistence boundary

- **Seeded Nimbus store.** I initialize every store with a frozen copy of data/catalog.ts before accessing browser storage. I persist the initial seed only after hydration, and accept validated Nimbus writes through the same catalog and publication methods as local companies. I keep NIMBUS_SEED_VERSION separate from envelope schema v2 and increment it when the supplied catalog changes. A matching saved seed version can restore Nimbus; a different or missing version restores the current seed and clears only Nimbus's pending moves, preserving valid local catalogs, their operations and active selection. I migrate the known schema v1 company envelope to v2; unknown schemas remain untouched until a deliberate mutation. Seed recovery has an explicit storage notice.
- **Route-safe catalog codes.** I reserve new for the plan creation route and reject it in both step validation and publication checks, with an explanation to choose another code. I validate persisted plan codes against the existing lowercase snake_case pattern and the same reservation before restoring a catalog.

- **Prototype persistence, same domain.** I use localStorage to simulate API persistence in this prototype and keep every saved organization in the existing Catalog shape. I centralize storage access in lib/organization-store.ts and keep validation pure in lib/validate-catalog.ts. I can replace the adapter later without changing derive rules; a real API would still require asynchronous loading/error handling in its consumers.
- **Explicit hydration.** I construct the store without reading window or storage and retain a stable seeded server snapshot for useSyncExternalStore, even after the live snapshot changes. I load only through idempotent hydrate after mount and publish immutable snapshots. Nimbus server HTML and its first client render use the same seed, with no company-loading screen; valid saved changes replace it afterward. I accept and document that content update. Local companies wait for hydration. The root layout supplies providers, while each route delegates shell and content to the shared stored dashboard.
- **Versioned, defensive reads.** I use a namespaced key and a versioned envelope containing catalogs, the active organization ID, pending operations and the seed version. I check nested union shapes, safe nonnegative integers, identities, route-safe plan codes and references before trusting a Catalog. I skip invalid or duplicate entries while retaining valid companies; malformed JSON or unsupported schemas leave the Nimbus seed available. I fall back to Nimbus for a missing active ID and expose recovery status rather than silently claiming all saved data loaded.
- **Session fallback.** I catch storage getter/read/write/remove failures and keep validated changes in memory. I show a status notice explaining that new session changes will not survive reload and that previous browser data may remain. I retain recovery notices when navigating companies. I copy/freeze snapshots to prevent accidental external mutation and do not retry a failed adapter during the same instance's session.
- **Reset to the seed.** I reset memory to one frozen Nimbus seed, clear every pending move and created company, and return the active ID to Nimbus. I remove only the organization storage key, preserving theme and unrelated site data; the next hydration starts from the seed again. If removal is blocked, I still reset memory and report memory mode; I cannot promise previously saved browser data was erased.
- **Company-scoped routes.** I retain Nimbus's root URLs and use /organizations/[organizationId] for other catalogs. organizationPath returns root paths for Nimbus and scoped paths for local companies, including creation, cancel, reset and overview navigation. I scope catalog links, version/comparison queries, alert anchors, sidebar state and breadcrumbs to the current company. The URL is authoritative; missing companies have a recovery view. Plan metadata is generic until the dashboard updates the title from stored data.
- **Shared dashboard, isolated data.** I feed overview, detail, packs, sidebar plans, alerts, page titles and switcher options from the same active store catalog. I use the neutral StoredCatalogDashboard and StoredCatalogContent names while retaining their existing module paths. The switcher lists the store's Nimbus and local companies without a separate stale built-in option. Creation reads the latest snapshot and saves only that catalog before showing completion with scoped navigation actions. I keep source data and domain types unchanged.
- **Deliberate reset.** I place Reset demo below dashboard content and require an explicit reset button after explaining that it restores Nimbus, removes created companies and clears all pending moves. I return to Nimbus's root overview and retain theme/unrelated keys. I do not use localStorage.clear or a single-click destructive action.
- **Prototype limits.** I do not provide authentication, backend synchronization, cross-device sharing, draft recovery or cross-tab conflict resolution. Each provider uses its own in-memory snapshot; simultaneous tabs can overwrite one another's stored changes. A production API needs asynchronous states and concurrency control, not just a different storage getter.
